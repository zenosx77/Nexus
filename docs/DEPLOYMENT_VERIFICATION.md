## 2. Implemented changes

### Trainer/browser integrity

- `trainer/train.py`, `tools/model-contract.cjs`, `index.html`: upload hashes and stores the exact canonical bytes generated by the actual browser canonicalizer, including JS exponent formatting, DEL/non-ASCII escaping, Unicode key ordering and signed zero. Python now requires Node 22 and the repository's browser file/helper.
- Validate the entire model before upload and before browser mutation: correct kind, supported timeframes, nonempty strategy weights, finite/ranged win rates, integer trade counts within 0–5000, and rejection of prototype-sensitive strategy names. A correctly hashed malformed later timeframe cannot partially modify an earlier timeframe.
- Storage objects are not overwritten. Read back exact bytes before registration; validate registry checksum/payload after registration. Validate deployed priors and rollback candidates before use. Existing weight blending and valid browser merge rules remain unchanged.
- Only `is_valid is True`, decisive win/loss, CALL/PUT browser non-shadow records enter training. Embedded outcome object/list shapes are handled. SQL filters precede pagination; local validation precedes count, hash and split. Exclude malformed/future targets and predictions recorded after their target. Explicit 1000-row pages, at most 5000 source rows per lookback.
- Chronological splitting purges labels that finish at/after the next validation boundary, including equal-time cross-pair records. Reject a deployed prior with missing/overlapping dataset provenance instead of contaminating evaluation.
- Training is **shadow-only**, even if the old DB setting says `auto_promote=true`. Candidate gates remain; no scheduled active-model replacement is possible. A separately reviewed promotion mechanism is still required.
- Trainer HTTP errors suppress response bodies; top-level failures return exit 1 without traceback/credentials.

## 4. Outstanding blockers and limits

1. **Shared-account quota is NOT enforced by current schema.** Migration 0007 counts worker traffic, 0008 independently counts browser relay traffic. Existing defaults permit worker 700/day, 6/min and browser 700/day, 7/min. Preserving these existing configs is not proof the single account stays under 700/day and six/minute. Do not enable schedules alongside browser traffic until a shared atomic budget migration/design is approved, implemented and verified. No budget reset, reduction, credential remap or migration has been performed here.
2. Production migration history, RLS/grants/indexes, models bucket privacy, secret presence, Actions settings and relay configuration remain unknown. Verify before even paid manual tests. Deployment requires separate approval.
3. Browser-recorded predictions remain mandatory. Worker ingestion/settlement **does not generate predictions**. No browser activity legitimately yields no training data/outcomes. Anonymous mirroring is preserved; it is not cryptographic proof of prediction authenticity. Untrusted client votes can still poison training; shadow-only operation and provenance review remain important.
4. Replay metrics are **simulated signal-quality proxies**, not realized returns or proof of profitability. Inferring alternate votes from recorded net outcomes is not a complete counterfactual trading simulator. Repeated holdout reuse/model selection also requires statistical controls before any profitability claim.
5. Trainer may now refuse old malformed/checksum-incompatible priors or overlapping prior windows. This is intentional fail-closed behavior. Late mirrors are excluded conservatively, reducing dataset size. Bounded dataset retrieval is not a global snapshot; concurrent historical corrections need a reviewed snapshot strategy for stronger reproducibility.
6. Registry promotion/legacy rollback updates are not one atomic transaction. Do not use the legacy rollback CLI in production until an approved transactional change is prepared. Registration failure can leave an orphan immutable Storage object or a `running` training row; inspect and reconcile with approval, never silently deploy it.
7. Stale candle counts remain visible even when database readback verifies writes. `verified` plus `stale > 0` is **not** healthy fresh ingestion. Weekend/holiday closures require operator context. Outcome processing is bounded at 200 rows/pass; large backlogs can exceed the intended waiting window.
8. Manual data invocations and other worker instances add traffic beyond scheduled theoretical totals. Persistent locks and budget guards remain necessary. Fixed-minute reservation windows are not proof of a provider rolling-minute cap. Existing provider retries are bounded by configured key count and, in jobs, six paid attempts; permanent provider errors may still consume failover credits.
9. GitHub concurrency limits overlap within these workflows, not independent external worker/trainer processes. GitHub can replace an older pending concurrency run; scheduling is best-effort, not an SLA. No live hosted load/concurrency test was performed.

## 5. Quota and refresh calculations

- Two runs/hour × 24 hours = **48 scheduled runs/day**.
- At most six paid attempts/run ⇒ **288 calls/day** from scheduled ingestion, including retries, assuming only one ingestion invocation per run.
- Existing worker planning allowance: `700 × 0.8 = 560` ingestion calls/day; **288 < 560 < 700**. The 560 allowance is cadence planning, not a separate database hard counter.
- At most 700 − 288 = **412** nominal daily account calls remain for *all* browser/backfill/other traffic, before manual runs/failures. This arithmetic does not solve shared minute contention or enforce reservations.
- `INGEST_PAIRS` is a comma-separated list of existing pair codes, e.g. `EUR/USD,GBP/USD`. Unset uses all active DB pairs. Up to six pairs rotate per pass; approximate full refresh is `30 × ceil(pair_count/6)` minutes: 1–6 pairs ≈30 min, 7–12 ≈60 min, 13–18 ≈90 min. Failovers/deferred runs may be slower. Large pair sets can outrun the settlement waiting window.
- 360 default 1-minute candles/request cover roughly six hours when supplied by the provider; this does not guarantee gap-free history. Polling every 30 minutes is not a live tick feed. Browser traffic remains separate and shares the account in reality.

## 7. Rollback and monitoring

- With approval, set `NEXUS_SCHEDULE_ENABLED` to anything except exact `true`, or remove it. This stops future cron execution, not queued/running jobs or external worker processes. In Actions → run → Cancel, separately cancel queued/running data/training runs. Check for independent legacy workers before recovery.
- Revert reviewed code via a new PR; never force-push or reset the repository/history. Disabling schedules is the first containment step before reverting integrity fixes. Older code may restore known checksum/settlement bugs—do not deploy blindly.
- Model restoration: identify a previous preserved registry row, validate its entire payload/checksum and Storage object, compare provenance/metrics, then request approval for a **transactional** active-model swap that keeps exactly one deployed version and retains every historical row/object. Current legacy two-step rollback is not approved as an atomic recovery method. Browser users must explicitly reapply a validated version; server state alone does not undo already merged local browser weights.
- Monitor every job's failed/deferred/verified verdict; candle freshness per active pair; missing outcomes past horizon+90m; invalid reason counts; duplicate settlement count; API scope counters and provider usage; training rows left `running`; failed uploads/registry readbacks; browser checksum/schema failures; storage growth and Actions runtime.
- Expected initial alerts/thresholds: any duplicate, guard-unavailable, checksum mismatch or storage failure requires investigation; stale >0 during expected market-open ingestion needs review; missing outcomes beyond 90m require candle/queue investigation. Pair count, closures and cron delay must inform thresholds.
- Quota recovery: wait for the actual minute/day reset, repair connectivity/configuration with approval, and retry a bounded job. Never reset budget tables, weaken constraints, delete outcomes/history, mint fake results or rotate credentials to evade provider limits.
- No automatic retention job was introduced. Storage/orphan cleanup requires evidence and approval; retain model/dataset provenance for audit.
